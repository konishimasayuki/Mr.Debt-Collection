# データ保存の設計

作成: 2026-07-27 / 全面改訂: 2026-07-31(画面と仕組みの作り替えに合わせて)

自社割賦の入金管理台帳。電話を受ける担当者と、数字を聞く経営者の両方が使う。
記録はサーバーに保存する。画面はデータベースに直接触らない。

> **2026-07-31 の作り替えについて。** 画面を5つのタブ(顧客一覧・入金登録・入金履歴・
> 未入金・設定)に作り替え、それに合わせてテーブルとAPIも作り直した。
> 旧版の設計(contract / bonus_months / dunning_reason / status など)は
> この文書では持たない。旧版で議論した決めごとのうち、いまも効いているものは
> 下に書き直してある。落としたものは「今回落としたもの」に並べた。

## どこに置くか

| | 選定 | 理由 |
|---|---|---|
| 画面 | React + Vite(`src/`)、`dist/` に静的ビルド | タブ切替と表が主で、ルーターも状態管理も要らない規模 |
| 置き場所 | Vercel + Neon(PostgreSQL) | 公開先がVercel。管理先を増やさない |
| 通信 | 画面 → `/api/*` → データベース | 画面から直接データベースに触らせない |
| 認証 | クッキーの簡易ログイン。利用者名とパスワードは環境変数。後で担当者ごとの利用者に置き換える | 仕様どおり「ログインは後回しでよいが、記録の『誰が』欄は最初から持つ」 |

**バックアップはデータベース側の自動バックアップを使う。**
端末のブラウザには保存しない(端末を替えると消えるため、引き継ぎの目的に反する)。

## テーブル

定義は `api/_schema.js`。金額はすべて**円の整数**(小数を使わない)。日付は日付型。
`POST /api/setup` で作る。何度実行しても同じ結果になる(`IF NOT EXISTS`)。

### 1. company(債権会社)

`id, name(一意), note, active, created_at`

設定タブから足す。**譲渡会社と譲渡先を1つの表で持つ。**
同じ会社が両方に来ることがあるため、種別で表を分けない。

顧客が使っている会社は消さず `active=false` にする。過去の顧客の表示が壊れるため。

### 2. customer(顧客・契約)

`id, name, kana, gender, birthday, address, tel, email, contract_date, car,
assignor_id(債権譲渡会社), assignee_id(債権譲渡先),
monthly_amount, term_count, pay_day, start_date, total_amount, memo, archived,
created_at, updated_at`

- `kana` は**あいうえお順の並びと、CSVの名寄せの両方**に使う
- `tel / email` は**権限を分ける対象**(仕様に明記あり)
- 1顧客 = 1契約。同じ人が2台買えば2行になる
- 二重登録は **氏名+月額+開始日**で弾く。同姓同名は弾かず、件数を返して画面で知らせる

### 3. schedule(支払予定)

`id, customer_id, no(回次), due_date, planned_amount, state, UNIQUE(customer_id, no)`

顧客登録時に回数ぶん一括で作る(`makeSchedule`、1回のINSERT)。
`state` は `未入金 / 一部入金 / 入金済み`。

- **期日は固定。** 契約で決まった日であり、入金約束をしても動かさない
- 月末は丸める。27日固定でも2月は28日(閏年は29日)、4月30日、と自然に落ちる(`dueOf`)

### 4. payment(入金)

`id, customer_id, paid_on, amount, method, source, ref_no, payer_name, memo,
import_key(一意), recorded_by, created_at, updated_at`

- `method` は `振込 / 現金 / その他`
- `source` は `CSV / 手動`。**画面で行の背景を変えるために持つ**
- `customer_id` は NULL を許す。CSVで照合できなかった入金を、
  捨てずに「割り当て待ち」として置いておくため
- `import_key` は二重取込を弾く鍵。銀行の照会番号(付番)は重複しうるので、
  **日付|付番|金額|振込人名(正規化)|同一ファイル内の連番**で作り、一意制約で弾く

### 5. allocation(充当)

`id, payment_id, schedule_id, amount`

**入金に予定IDを1本だけ持たせない。** まとめ払いを1件の入金として受け、
複数の回へ按分する。残高は Σ充当額 で出す(`allocate`)。

- 古い回から順に充てる
- **満額に届くまで `schedule.state` は `一部入金`**。届いてはじめて `入金済み`
- 分割入金(1回ぶんを3日後と5日後に分けて払う)も同じ仕組みで扱う
- 入金を直す・消すときは、いったん充当を外して入れ直す。
  顧客を付け替えたときは**両方の顧客の記録に残す**

### 6. promise(入金約束)

`id, customer_id, promised_on, until_time, schedule_no, amount, memo, done, created_by, created_at`

顧客ページの月カレンダーで、日付を押して足す。

- **1回ぶんに何件でも足せる。** 「3日後に半分、5日後に残り」が日常のため。上書きしない
- `until_time` が NULL なら終日。入っていれば「その時刻まで」
- **約束は `schedule.due_date` を動かさない。**
  以前は約束のたびに期日を更新していたが、分割の約束を何件も足すようになり
  期日が跳ね回って契約上の期日が分からなくなるため取りやめた(2026-07-29 決定)
- 動かす・消すこともできる。消しても、消したことは `event` に残る

### 7. payer_alias(名寄せ辞書)

`id, normalized_name(一意), customer_id, created_by, created_at`

一度人が紐付けたら永続化し、次のCSVから自動で当たるようにする。

### 8. event(記録)— 追記のみ

`id, customer_id, payment_id, occurred_at, recorded_by, kind, text, memo`

**更新も削除もしない。** 訂正は「取消」を足す。
`BEFORE UPDATE OR DELETE` のトリガで、データベース側でも禁止している。

## 名前の正規化(検索と名寄せ)

`api/_lib.js` の `norm()`。次の順で潰す。

1. `NFKC` — 半角カナ→全角カナ、全角英数→半角英数
2. ひらがな→カタカナ(`+0x60`)
3. 空白(半角・全角)を落とす
4. 記号・カッコ・中黒・長音・ハイフンを落とす
5. 小文字にする

これで **かな / 全角カナ / 半角カナ / 半角英字 / 全角英字**のどれで打っても
同じ顧客に当たる。入金履歴の顧客検索も、CSVの名寄せも同じ関数を使う。

## CSVの取り込み

`api/_csv.js` が形式を自動で見分ける。

- **全銀協規定形式(種別03)** — レコード1/2/8/9 の並びで判定。Shift-JIS、
  和暦 YYMMDD(令和 = 2018+N)。入払区分 1=入金 のみ取り、取引区分 19=訂正 は飛ばす。
  トレーラの件数・合計で検算する
- **ふつうのCSV** — 見出し行のことばで日付/付番/金額/振込人を当てる。
  見出しが無ければ位置で読む

### 3つの呼び方

| 送るもの | すること |
|---|---|
| `{text}` | 読んで照合するだけ。**保存しない**。明細と重複の印を返す |
| `{実行:true, 明細:[...]}` | 画面で残した行だけを保存する |
| `{割当:{...}}` | 照合できなかった1件を、人が選んだ顧客の入金にする |

**プレビューで消せる。** 銀行のファイルには台帳と関係ない入金も混ざるため、
取り込む前に行を外せるようにしてある。外した行は入らない。

**重複の印。** `日付|付番|金額` が同じ行に印を付ける。印は注意を促すだけで、
取り込みは止めない(同じ日に同じ人から同じ額が2件、は実在する)。
本当に二度目のときは `import_key` の一意制約が弾く。

### 名寄せの順序

1. `payer_alias`(前に人が紐付けた名前)
2. 顧客の「よみ」または氏名との完全一致
3. **登録した読みで始まるか**(長い読みを優先、2文字以上のみ)。
   銀行の振込依頼人名は「ｷﾑﾗ ﾕｳｽｹ」と下の名前まで入るため、苗字だけの登録でも当たる
4. それでも複数残れば**月額で絞る**
5. 決まらなければ人に回す(画面で顧客を選ばせ、選んだ紐付けを `payer_alias` に覚える)

同姓が実在する(実データで田中3名・サイトウ2名・山田2名・松本2名)。
いずれも月額が違うので4で絞れているが、**下の名前まで「よみ」に入れれば**その迷いは消える。

## 未入金の判定

**期日を過ぎて、その回にまだ残りがある人。** あいうえお順で並べる。

差額は1円でも見る決めごとだが、差額だけでは足りない。
分割入金の途中は差額が動かないため、期日と残りで見る必要がある。

## APIの形

Vercel の関数は1ファイル1エンドポイント。ESM(`export default`)で書く。

| | |
|---|---|
| `GET/POST/DELETE /api/session` | ログイン状態 / ログイン / ログアウト |
| `GET /api/customers` | 顧客一覧(あいうえお順) |
| `GET /api/customers?未入金=1` | 未入金タブの一覧 |
| `POST /api/customers` | 新規顧客登録。支払予定も同時に作る |
| `GET /api/customer?id=` | 顧客ページ一式(支払予定・入金・約束・記録) |
| `PATCH /api/customer` | 顧客の情報・メモを直す |
| `POST /api/customer` | `種類: 約束 / 約束変更 / 約束削除` |
| `GET /api/payments` | 入金履歴(既定30件、当日から降順)。`検索=` で顧客名を絞る |
| `POST /api/payments` | 手動入金(**メモ必須** — 手で入れた理由を残すため) |
| `PATCH/DELETE /api/payments` | 入金を直す / 消す。充当も付け直す |
| `POST /api/import` | CSV(上の3つの呼び方) |
| `GET/POST/PATCH/DELETE /api/companies` | 債権会社 |
| `POST /api/setup` | テーブルを作る |
| `POST /api/setup {載せ替え:true}` | 旧台帳54件を新しい形へ入れる |

**書き込みはすべて記録者を伴う。** いまは簡易ログインの利用者名を入れ、
担当者ごとの利用者を作ったらそれに置き換える。

**`sql` は `sql(text, params)` の形で呼ぶ。** `@neondatabase/serverless` の
`neon(url)` が返す関数はそれ自体がクエリ実行で、`sql.query()` は無い。

## 既存データの載せ替え

`POST /api/setup {載せ替え:true}`(設定タブの「既存データを載せ替える」)。

`api/data/contracts.json` の54件を、氏名で照合しながら入れる。
**すでに居れば飛ばす。**何度押しても増えない。

- 支払総額は**月額×回数**で入れ直す(旧台帳の総額はボーナス加算を含んでいたため)
- 旧台帳のボーナス見込みと「回収」あつかいは、消さずに顧客のメモへ文章で残す
- 旧台帳に無い項目(債権譲渡会社・債権譲渡先・よみ・性別・生年月日・住所・
  電話番号・契約日)は空のまま。設定タブで会社を登録してから顧客ページで入れる

## 今回落としたもの

作り替えの指示にある5つのタブに無いため、いまは持っていない。
必要になったら、旧版の設計(git の履歴)から戻せる。

| 落としたもの | 旧版でどう扱っていたか |
|---|---|
| ボーナス加算 | `bonus_months / bonus_each / bonus_remaining` と充当の kind。載せ替え時にメモへ文章で残している |
| 督促とめ(理由つきの解除) | `dunning_reason / dunning_by / dunning_at / dunning_until` |
| 契約の状態(回収・弁護士介入など) | `contract.status`。ADR-008 |
| 累計差額と過不足の処理方針 | `balance_diff / diff_plan` |
| 現金の受領日と預入日の別持ち | `payment.deposited_on` |
| 充当の kind(元本・手数料・遅延損害金…) | `allocation.kind` |
| 開始時の入金実績(オープニング) | `/api/opening`。**載せ替え直後は全件が未入金から始まる** |

**オープニングは作り替えで最も影響が大きい。** 旧台帳から載せ替えただけでは、
すでに何回目まで払い終えているかが入らず、全員が1回目から未入金に見える。
運用に乗せる前に、入金履歴か手動入金で過去分を入れる必要がある。
