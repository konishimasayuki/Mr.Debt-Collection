# データ保存の設計

作成: 2026-07-27 / 全面改訂: 2026-07-31(画面と仕組みの作り替えに合わせて)

自社割賦の入金管理台帳。電話を受ける担当者と、数字を聞く経営者の両方が使う。
記録はサーバーに保存する。画面はデータベースに直接触らない。

> **2026-07-31 の作り替えについて。** 画面をタブ(顧客一覧・入金登録・入金履歴・
> 未入金・終了・設定)に作り替え、それに合わせてテーブルとAPIも作り直した。
> 旧版の設計(contract / bonus_months / dunning_reason / status など)は
> この文書では持たない。旧版で議論した決めごとのうち、いまも効いているものは
> 下に書き直してある。落としたものは「今回落としたもの」に並べた。

## どこに置くか

| | 選定 | 理由 |
|---|---|---|
| 画面 | React + Vite(`src/`)、`dist/` に静的ビルド | タブ切替と表が主で、ルーターも状態管理も要らない規模 |
| 置き場所 | Vercel + Neon(PostgreSQL) | 公開先がVercel。管理先を増やさない |
| 通信 | 画面 → `/api/*` → データベース | 画面から直接データベースに触らせない |
| 認証 | クッキーの簡易ログイン。利用者名とパスワードは環境変数。後で担当者ごとの利用者に置き換える | 仕様どおり「ログインは後回しでよいが、記録の『誰が』欄は最初から持つ」 |

**バックアップはデータベース側の自動バックアップを使う。**
端末のブラウザには保存しない(端末を替えると消えるため、引き継ぎの目的に反する)。

## テーブル

定義は `api/_schema.js`。金額はすべて**円の整数**(小数を使わない)。日付は日付型。
`POST /api/setup` で作る。何度実行しても同じ結果になる(`IF NOT EXISTS`)。

**テーブルが足りないときは、自動で作り直す。** `api/_db.js` が、問い合わせが
`42P01`(undefined_table)で落ちたときだけ `STATEMENTS` を流し、一度だけやり直す。
テーブルを増やしても、デプロイするだけで追いつく(画面から押す場所は無いため)。
ふだんは通らない道なので、速さには響かない。

**旧台帳のテーブルが残っているデータベースでは、先に退避する。**
`schedule` `payment` `allocation` `promise` `payer_alias` `event` は新旧で名前が同じで
中身が違う(旧は `contract_id`、新は `customer_id`)。残っていると `IF NOT EXISTS` が
読み飛ばし、新しい列に索引を張るところで
`column "customer_id" does not exist` で落ちる。

`api/setup.js` の `moveOldTables()` が、旧台帳の7つを `old_ledger` スキーマへ移す。
**消さない**(手で入れたオープニングが入っているため)。
旧台帳にしかない `contract` があるかどうかで見分けるので、二度目は何もしない。

### 1. company(債権会社)

`id, name(一意), note, active, created_at`

設定タブから足す。**譲渡会社と譲渡先を1つの表で持つ。**
同じ会社が両方に来ることがあるため、種別で表を分けない。

一覧は**登録した順**で出す。名前順にすると、あとから足した会社が先頭に来て
「逆に入っている」ように見えるため(2026-07-31)。

**顧客に使われている会社は削除できない**(400で断る)。過去の顧客の表示が壊れるため。
消したいときは、先にその顧客の債権譲渡会社・債権譲渡先を変える。

`active` 列は残っているが**使っていない**。以前は「選べる／使わない」の切り替えを
画面に置いていたが、必要な場面が説明できず外した(2026-07-31)。

### 2. customer(顧客・契約)

`id, name, kana, gender, birthday, address, tel, email, contract_date, car,
assignor_id(債権譲渡会社), assignee_id(債権譲渡先),
monthly_amount, term_count, pay_day, start_date, total_amount, memo,
status(通常/回収), status_date(回収した日),
debit_state(口座振替の手続き), debit_date,
bonus_months(ボーナスの月), bonus_day, bonus_amount,
is_test(動作を試すための顧客), archived, created_at, updated_at`

- `kana` は**あいうえお順の並びと、CSVの名寄せの両方**に使う
- `tel / email` は**権限を分ける対象**(仕様に明記あり)
- 1顧客 = 1契約。同じ人が2台買えば2行になる
- 二重登録は **氏名+月額+開始日**で弾く。同姓同名は弾かず、件数を返して画面で知らせる
- `is_test` が真の行は**動作を試すための顧客**。画面では「テスト」の印を付け、
  本物と見間違えないようにする。設定タブから作り直し・削除ができる(`/api/testcustomer`)。
  **未入金タブの人数と合計には入れない**。経営者が見る数字に試し打ちの金額を混ぜないため

### 終わった取引 ─ `status` と「完済」(2026-08-05 / 呼び名を2026-08-07に改訂)

**車両を引き上げたら、そこで終わり。督促も請求もしない。**

`status` は `通常 / 回収` の2つだけ。**完済はここに入れない。**
完済は入金から決まるもので、入金を取り消せば完済でなくなる。
列に持つと二重管理になってずれるため、その都度 `schedule` から判定する。

**DBの値は今も `回収`。画面での呼び名だけ「引き上げ」に変えた。**
ダッシュボードで「回収」がすでに**入金の意味**(回収率・未回収額)で使われており、
車両の引き上げと紛らわしいため。値そのものを変えると本番の既存データ(旧台帳の3名)を
移行しなければならず、その移行は自動では走らない(下記)ので、値は据え置いた。
`api/_list.js` が返す `終了理由` の**出し先の文字列**だけを `引き上げ` に変えている
(`c.status === '回収' ? '引き上げ' : …`)。DB の値そのものと、画面に出す文字列は
ここで初めて分かれた。

| | どこで決まる | 引き上げた日 |
|---|---|---|
| 引き上げ(DB値は`回収`) | 人が顧客情報の編集で選ぶ | `status_date` |
| 完済 | 全部の回が入金済みかで自動 | 持たない |

どちらも**終了**として扱い、`GET /api/customers` が `終了` `終了理由` を返す。
タブの見出しは**完済/引き上げ**(2026-08-07。以前は「終了」)。

- **未入金タブから外す。** 引き上げた方に督促の電話をかけないため。ここがいちばんの実害
- **顧客一覧からは消さない。** 名前で探されたときに見つからないと困る。
  代わりに行を薄いグレーにして、印を付ける
- 完済/引き上げタブ(`?終了=1`。クエリの名は変えていない)に並べる。
  **引き上げは朱色、完済は薄い黄色**で分ける
- 旧台帳の載せ替えでは、`kaishu` が真の3名を最初から `status='回収'` で入れる。
  通常で入れると、期日が来たとたんに未入金へ出てしまう

### 口座振替(自動引き落とし)─ `debit_state` と `debit_date`

手続きの状態だけを持つ。**その月落ちたかどうかは持たない**。
それは入金があったかどうか(`schedule.state`)ですでに表せているため。

`未申込 / 口座振替申込 / 口座振替開始 / 口座振替停止` の4つ。**全員まず「未申込」**。
日(`debit_date`)がいるのは**申込と開始だけ**。停止と未申込にすると空になる。
日を省いて送ると**当日**が入る。

顧客ページのカレンダーの上の帯に出し、**押すとその場で変えられる**。
引き落としのトラブルが多く、電話中に聞かれるため、見えて・すぐ直せる場所に置く。
日付の欄は `<input type="date">`。スマホでは端末のホイール、パソコンでは
年/月/日 の直接入力になる（両方を1つの書き方で満たせる）。

### 3. schedule(支払予定)

`id, customer_id, no(回次), kind(通常/ボーナス), due_date, planned_amount, state,
UNIQUE(customer_id, kind, no)`

顧客登録時に回数ぶん一括で作る(`makeSchedule`、1回のINSERT)。
`state` は `未入金 / 一部入金 / 入金済み`。

- **期日は固定。** 契約で決まった日であり、入金約束をしても動かさない
- 月末は丸める。27日固定でも2月は28日(閏年は29日)、4月30日、と自然に落ちる(`dueOf`)

### ボーナス払い(2026-08-05)

「7月と12月の10日に10万円」のように、**月を複数選んで**足す。
`bonus_months`(月の配列) / `bonus_day` / `bonus_amount` の3つだけ持つ。

**予定は同じ `schedule` に `kind='ボーナス'` として入れる。** 別の表にしない。
同じ表に入れておけば、充当も残債も未入金の判定もそのまま動く。

- **回次は通常とボーナスで別に数える。** 画面では「全48回 + ボーナス4回」と出す。
  そのため一意の決まりは `(customer_id, kind, no)`
- **充当は期日の古い順**(`ORDER BY due_date, kind, no`)。
  ボーナスが通常の回のあいだに割り込むので、`no` だけで並べると順が狂う
- 契約の期間(初回の期日 〜 最終回の期日)に入る月だけ作る(`bonusDues`)
- 月末は通常と同じく丸める。2月31日 → 2月28日
- `total_amount` にボーナスぶんを足す。残債はここから引いて出すため

**設定を変えても、入金が充てられているボーナスの回は消さない**(`remakeBonus`)。
消すと入金の行き先が消える。入金のない回だけ作り直し、回次は期日順に振り直す。

画面では次のように出す。

| どこ | 出し方 |
|---|---|
| 顧客情報の編集 | 12か月の札を押して選ぶ。日と金額は選んでから出す |
| カレンダー | 紫の印で「賞与◯回目」。凡例も**ボーナスがある人だけ**出す |
| 支払いの記録 | 見出しは**ボーナスがある人だけ**「全48回 + ボーナス4回」。行は期日順 |
| カレンダー上の帯 | いま追いかけている回がボーナスなら「ボーナス◯回目 / 全◯回」 |
| 未入金 | **遅れているのがボーナスの回なら、名前の横に「ボーナス」**。金額が大きいので、通常の回と同じ扱いで電話すると話が食い違う |

回メモ(`schedule_memo`)は**通常の回にだけ**出す。`schedule_no` だけでは
通常1回目とボーナス1回目が区別できないため。

### 4. payment(入金)

`id, customer_id, paid_on, amount, method, source, ref_no, payer_name, memo,
import_key(一意), recorded_by, created_at, updated_at`

- `method` は `振込 / 現金 / その他`
- `source` は `CSV / 手動`。**画面で行の背景を変えるために持つ**
- `customer_id` は NULL を許す。CSVで照合できなかった入金を、
  捨てずに「割り当て待ち」として置いておくため
- `import_key` は二重取込を弾く鍵。銀行の照会番号(付番)は重複しうるので、
  **日付|付番|金額|振込人名(正規化)|同一ファイル内の連番**で作り、一意制約で弾く

### 5. allocation(充当)

`id, payment_id, schedule_id, amount`

**入金に予定IDを1本だけ持たせない。** まとめ払いを1件の入金として受け、
複数の回へ按分する。残高は Σ充当額 で出す(`allocate`)。

- 古い回から順に充てる
- **満額に届くまで `schedule.state` は `一部入金`**。届いてはじめて `入金済み`
- 分割入金(1回ぶんを3日後と5日後に分けて払う)も同じ仕組みで扱う
- 入金を直す・消すときは、いったん充当を外して入れ直す。
  顧客を付け替えたときは**両方の顧客の記録に残す**

### 6. promise(入金約束)

`id, customer_id, promised_on, until_time, schedule_no, amount, memo, done, created_by, created_at`

顧客ページの月カレンダーで、日付を押して足す。

- **1回ぶんに何件でも足せる。** 「3日後に半分、5日後に残り」が日常のため。上書きしない
- `until_time` が NULL なら終日。入っていれば「その時刻まで」
- **約束は `schedule.due_date` を動かさない。**
  以前は約束のたびに期日を更新していたが、分割の約束を何件も足すようになり
  期日が跳ね回って契約上の期日が分からなくなるため取りやめた(2026-07-29 決定)
- 動かす・消すこともできる。消しても、消したことは `event` に残る

### 7. schedule_memo(回ごとのメモ)

`id, customer_id, schedule_no, text, auto, promise_id, created_by, created_at, updated_at`

支払いの記録の**各回の下**に出る。入金約束を入れると自動で1行足す(`auto=true`)。

- **記録(`event`)とは別の表。** あとから直せるし消せる必要があるため
- 画面は**新しい順に3件**まで出し、それより古いものは折りたたむ
- 回が決まっていない約束(「どの回ぶん」を決めない)は、出す場所が無いので足さない
- 消したことは `event` に残る

### 約束の写しのメモは、約束と食い違わせない

`promise_id` の入ったメモは**その約束の写し**。約束1件につき1行で、
**約束の今の姿を映す**(2026-08-05)。

- 約束を直したら、行を増やさずに**その行の文を書き換える**。
  増やすと、同じ約束の古い金額がいつまでも並び、どれが本当か分からなくなる
- 約束を取り消したら、その行を**消して「取り消し」の1行を入れ直す**。
  書き換えでは元の位置に留まり、古い約束のぶんは折りたたみに隠れて見えない。
  行数は増えない
- 画面では**文を直接編集させない**。「約束を変更」を出し、カレンダーの
  約束編集へ送る。**メモの文を直しても約束は変わらない**ため、
  直せてしまうとカレンダーと食い違う(実際に起きた)
- 取り消し済みのメモは `promise_id` が空になるので、手書きのメモと同じく編集・削除できる
- 文面は `約束の文()` の1か所だけで組み立てる。別々に組むと直したときにずれる

経緯（いつ何円からいくらへ変えたか）は `event` に残るので失われない。

### 8. payer_alias(名寄せ辞書)

`id, normalized_name(一意), customer_id, created_by, created_at`

一度人が紐付けたら永続化し、次のCSVから自動で当たるようにする。

### 9. event(記録)— 追記のみ

`id, customer_id, payment_id, occurred_at, recorded_by, kind, text, memo`

**更新も削除もしない。** 訂正は「取消」を足す。
`BEFORE UPDATE OR DELETE` のトリガで、データベース側でも禁止している。

例外は**動作を試すための顧客(`customer.is_test`)の記録だけ**。作り直せなければ
試し打ちの跡が永久に残るため、削除だけ通す。更新はテスト顧客でも通さない。
消すときは**顧客の行より先に記録を消すこと**。顧客を消したあとではトリガの
`EXISTS` がもう当たらず、追記のみに引っかかる(`api/testcustomer.js`)。

## 名前の正規化(検索と名寄せ)

`api/_lib.js` の `norm()`。次の順で潰す。

1. `NFKC` — 半角カナ→全角カナ、全角英数→半角英数
2. ひらがな→カタカナ(`+0x60`)
3. 空白(半角・全角)を落とす
4. 記号・カッコ・中黒・長音・ハイフンを落とす
5. 小文字にする

これで **かな / 全角カナ / 半角カナ / 半角英字 / 全角英字**のどれで打っても
同じ顧客に当たる。入金履歴の顧客検索も、CSVの名寄せも同じ関数を使う。

## CSVの取り込み

`api/_csv.js` が形式を自動で見分ける。

- **全銀協規定形式(種別03)** — レコード1/2/8/9 の並びで判定。Shift-JIS、
  和暦 YYMMDD(令和 = 2018+N)。入払区分 1=入金 のみ取り、取引区分 19=訂正 は飛ばす。
  トレーラの件数・合計で検算する
- **ふつうのCSV** — 見出し行のことばで日付/付番/金額/振込人を当てる。
  見出しが無ければ位置で読む

### 読めなかった行は、黙って落とさない

`parseCsv` は `読み飛ばし: [{行, 理由, 中身}]` を必ず返し、画面の
「取り込む前の確認」に **何行を、なぜ取り込まないか**を出す(2026-08-05)。

理由は「出金の行です」「訂正の行です」「日付が読み取れません」
「金額が読み取れません」。1件も読めなかったときは、その理由を添えて断る。

**黙って落としてはいけない。** 列の並びが想定と違うと全部落ちるが、
取り込んだ件数しか見ていないと気づけない。入っていない入金を
未入金として督促してしまう。

### 文字コードの見分け方

**先に UTF-8 で読み、化けが無ければ UTF-8 と決める**(`readText`)。

UTF-8 はバイトの並びに決まりがあり、そうでないものを入れると必ず化ける。
一方 Shift-JIS はどんなバイトでもだいたい何かの字として読めてしまう。
そのため「化けの少ないほうを採る」と、**UTF-8 のファイルを Shift-JIS と
取り違える**(2026-08-05に直した)。取り違えると日本語の見出しが壊れ、
列を見つけられずに位置で読むことになり、列の並びが違うファイルでは
中身がまるごとずれる。

### 3つの呼び方

| 送るもの | すること |
|---|---|
| `{text}` | 読んで照合するだけ。**保存しない**。明細と重複の印を返す |
| `{実行:true, 明細:[...]}` | 画面で残した行だけを保存する |
| `{割当:{...}}` | 照合できなかった1件を、人が選んだ顧客の入金にする |

**プレビューで消せる。** 銀行のファイルには台帳と関係ない入金も混ざるため、
取り込む前に行を外せるようにしてある。外した行は入らない。

**重複の印。** `日付|付番|金額` が同じ行に印を付ける。印は注意を促すだけで、
取り込みは止めない(同じ日に同じ人から同じ額が2件、は実在する)。
本当に二度目のときは `import_key` の一意制約が弾く。

### 名寄せの順序

1. `payer_alias`(前に人が紐付けた名前)
2. 顧客の「よみ」または氏名との完全一致
3. **登録した読みで始まるか**(長い読みを優先、2文字以上のみ)。
   銀行の振込依頼人名は「ｷﾑﾗ ﾕｳｽｹ」と下の名前まで入るため、苗字だけの登録でも当たる
4. それでも複数残れば**月額で絞る**
5. 決まらなければ人に回す(画面で顧客を選ばせ、選んだ紐付けを `payer_alias` に覚える)

同姓が実在する(実データで田中3名・サイトウ2名・山田2名・松本2名)。
いずれも月額が違うので4で絞れているが、**下の名前まで「よみ」に入れれば**その迷いは消える。

## 未入金タブ（2026-08-07）

電話をかける人が使う名簿。**1画面に何人入るか**が使い勝手を決める。

- **行を押すと顧客ページが開く。**「顧客ページを開く」ボタンは外した。
  以前は行を押すと入金履歴へ飛んでいたが、電話中に見たいのは顧客ページのほう
- 行に残す操作は「手動入金登録」だけ。電話中にその場で入れられるようにする
- 名前の横に **`◯日 遅れ` / 督促の状況 / 約束の日** を並べる。
  督促の印は押せる（上記）。約束の日を過ぎていれば朱色で「超過」と出す
- 列は `顧客名 / 支払い期日 / 支払済回数 / 月額 / 支払日 / 残債 / 残回数`。
  「支払い回数」は**支払済回数**に改めた（残回数と紛らわしいため）

### スマホの札は2列に詰める

7項目を縦に積むと1件で7段になり、1画面に1人しか入らない。
**2列のグリッドにして、ラベルと値も横に並べる**（`.unpaid-cards`）。

- `支払い期日 ｜ 支払済回数` / `月額 ｜ 支払日` / `残債 ｜ 残回数` の3段
- 名前と操作は1列ぶち抜き。操作は `order` を指定していちばん下へ
  （指定しないと、共通の `.cards td.act{order:2}` が効いて途中に割り込む）
- これで1件がおよそ200px。詰める前は340pxだった

## 顧客一覧のあいうえお順と索引

電話帳と同じ形にする。**行（あ・か・さ…）ごとに見出しを差し込み、上に索引を置く。**

並び順と索引は `api/_yomi_dict.js` の `並び読み()` / `索引()` で決める。

1. 登録された「よみ」があればそれを使う
2. 無ければ**苗字の読みの辞書**で補う（旧台帳から載せ替えた54件は「よみ」が空のため）
3. 辞書にも無ければ「よみが分からない方」に置き、最後にまわす

辞書には読みが分かれる苗字（高野・恩地・小田・五島 など）も入っている。
**索引の位置が実際の読みと違うことがある。** その人の「よみ」を顧客情報の編集で
入れれば、そちらが優先される。

見出しは**1つの表の中に差し込む**（行ごとに表を分けない）。分けると
見出しの行が繰り返され、列の幅もそろわなくなる。

**索引を押したときの止まる位置。** ヘッダーと索引バーは画面の上に貼り付いたままなので、
その高さぶん手前で止めないと、肝心の見出しと最初の名前が裏に隠れる。
高さは端末と文字の大きさで変わるため、決め打ちにせず `App` が測って
`--head-h` に入れ、索引バーの `top` と飛び先の計算に使う。

**索引の色は、いま画面に出ている行に付く**(スクロールに追随)。決めごとが3つある。

1. **飛び先と判定の基準をそろえる。** ずれていると、押した直後に1つ手前の行が塗られる
2. **飛び先は「貼り付いたときの」帯の高さで計算する。** 画面のいちばん上にいるとき、
   索引バーはまだ流れの中にあり `bottom` が実際より下に出るため、
   そのまま使うと飛びすぎる
3. **最後のほうの行は、画面の下が足りず上まで送れない。**
   送れないと色も合わないので、最後の行の高さを測って足りないぶんの余白を足す

## 一覧の札（スマホ）

幅760px以下では表を札にする。作りはこう。

1. 見出し行(`thead`)を隠す
2. 各行(`tr`)を縦積みの箱にする
3. 各セル(`td`)を**左に項目名・右に中身**の横並びにする。
   項目名はセルの `data-label` から `::before` で出す
4. 左の項目名は幅を固定(7.6em)。残りが中身の幅になる

**札の見出しにするセルには `nm` を付ける。** 表の何列目かに縛らない
(入金履歴は1列目が日付で、見出しにしたいのは2列目の顧客名)。`order` で先頭へ出す。
札の下に置く操作は `act`(横いっぱいの帯にする)。

**セルの見た目を JSX に直接書かない。** 幅の上限や文字の大きさを直接書くと、
札のときに打ち消せない。実際、入金履歴のメモに書いた `max-width:260px` が
札でもそのまま効き、中身に164pxしか残らず11文字ほどで折り返していた(2026-08-01)。
`memo` `mono` `who` のように名前を付け、画面幅ごとに切り替える。

**モーダルを開いたとき、入力欄へ自動で移るのはキーボードのある端末だけ。**
日付や時刻の欄へ移ると、端末の日付選びが勝手にせり上がってくる(2026-08-05)。
指で操作する端末では、そもそも移らない。開いた瞬間にキーボードが出て
下の「登録する」が隠れるため。日付・時刻・月・ファイル・チェックは対象外。

**モーダル右上に「閉じる」は置かない。** スマホでは題と重なって読めなくなる。
閉じるのは下の「キャンセル」。どのモーダルにも必ず置く。
上の余白は `env(safe-area-inset-top)` を見る。見ないと題が時計の帯に潜る。

**ヘッダーのログアウトは小さくする。** タブのすぐ上にあり、誤って押しやすいため。
ほかのボタンは指で押す端末では44px以上にするが、ここだけ例外にしている。

## 未入金の判定

**期日を過ぎて、その回にまだ残りがある人。** あいうえお順で並べる。

差額は1円でも見る決めごとだが、差額だけでは足りない。

## 速さ ─ 問い合わせの「回数」ではなく「段数」を減らす

データベースは関数とは別の場所にある。**問い合わせ1回ごとに往復の待ち時間**が
かかり、これが体感の遅さのほとんどを占める。件数を減らすより、
**順番に待つ回数(段数)**を減らすほうが効く。守ること。

1. **関係のない問い合わせは `Promise.all` で同時に投げる。**
   顧客ページは7つ見るが、互いに関係がないので待ち時間は1つぶんで済む。
2. **行ごとにループの中で問い合わせない(N+1)。**
   `WHERE ... = ANY($1::int[])` や `unnest()` でまとめて1回にする。
   充当(`allocate`)・状態の付け直し(`restateMany`)・CSV取込はこれで書いてある。
3. **順番が要るものだけ順番にする。**
   同じ顧客の充当は古い回から埋めるので順番が要るが、**別の顧客どうしは関係がない**。
   CSV取込は顧客ごとに束ねて同時に進める。
4. **要らない行を持ってこない。** 入金履歴は、検索していないときは表示件数だけ取る。

実測(顧客57名・CSV50行、`scratchpad/t-rtt.mjs`)。段数がそのまま待ち時間になる。

| | 直す前の段数 | いまの段数 |
|---|---|---|
| 顧客一覧 / 未入金 | 3 | 1 |
| 顧客ページ | 7 | 1 |
| 入金履歴 | 1（2030行取得） | 1（30行取得） |
| 入金の取り消し | 8 | 6 |
| CSV取込(50行) | 450 | 6 |

画面側(`src/api.js`)も、同じ読み取りが重なったら1つにまとめ、
**5秒だけ**覚えておく。**書き込みのときは覚えているものを全部捨てる**
(送る前と送ったあとの両方)。金額を扱うので、古い数字は出さない。

### 開いた直後を速くする

台帳を開いた直後だけは、上の段数の話とは別の待ち時間が乗る。
**しばらく使われないと、関数もデータベースも眠る**(コールドスタート)。
起こすのに数秒かかり、2回目からは速い。ここは減らせないので、
**眠っているものを起こす回数を1回に減らす**。

1. **ログイン確認と顧客一覧を1回の通信にまとめる。**
   `GET /api/session?顧客=1` が、ログインの可否と一緒に顧客一覧を返す。
   一覧の組み立ては `api/_list.js` に置き、`/api/customers` と共用する。
   画面側は届いた一覧を `/api/customers` の控えに入れておくので、
   顧客一覧タブは取り直さない(`src/api.js` の `me()`)。
   **未ログインなら一覧は入れない。**合鍵の確認は今までどおりサーバーで行う。
2. **返事を待たずに枠を出す**(`src/App.jsx`)。
   ヘッダーとタブは先に描き、中身だけ骨組み(`Loading`)にする。
   ログイン画面と台帳のどちらを出すかは、
   **前にこの端末でログインできたか**を `localStorage` に覚えておいて決める。
   はじめて開いた端末だけは分からないので、そこだけ返事を待つ。
   これは**見た目のための覚え書きで、合鍵ではない**。
   覚え書きだけ立てても、サーバーが断れば一覧は出ない。
   ログアウトすると消す。
3. **関数をデータベースの近くで動かす**(`vercel.json` の `regions`)。
   Neon はシンガポール(東京は無い)。関数の既定は米国なので、
   放っておくと 日本→米国→シンガポール→米国→日本 と太平洋を2往復する。
   `"regions": ["sin1"]` にして、日本→シンガポールの1往復にした。

検査は `scratchpad/t-open.mjs`。
通信が `session` 1回だけであること、返事を1.5秒遅らせてもタブが先に出ること、
覚え書きだけでは中身が見えないことを見ている。

### 開いた直後に出すタブ(2026-08-07)

**ログインした直後・ページを更新した直後は、必ずダッシュボードから始める。**
`src/App.jsx` の `tab` の既定値を `'dash'` にしている。

- ページの更新は、コンポーネントが作り直されるので既定値だけで足りる
- ページを更新せずに**ログアウトしてまた入り直した**ときは、既定値では効かない
  (`tab` の state がそのまま残っているため)。そこで `Login` の `onDone` で
  `setTab('dash')` を明示的に呼んでいる
- 返事を待たずに枠を出す骨組み(上記)の見出しも「ダッシュボード」に合わせた

### 回を押して、その場でメモを足す(2026-08-07)

**回の行を押すと、その下に入力欄が出る。**電話を切った直後に、その回のことを
その場で書き足せるようにする。以前は API にしか口が無く、画面から足せなかった。

- 書いた**日と時刻**はサーバーが入れる(`created_at` の既定値 `now()`)。
  人が入れ間違えないし、あとから動かせない
- 画面には `08/07 09:12` の形で出す。**日本時間**に直してから返す
  (`to_char(created_at AT TIME ZONE 'Asia/Tokyo', …)`)。
  UTC のまま切ると、夜に書いたメモが前日の日付で出る
- 足したあとも欄は開いたまま、中身だけ空にする。続けて何件も足せるようにするため
- 送るのは「メモを足す」か **Ctrl/⌘ + Enter**。文章なので Enter は改行に使う
- **ボーナスの回は押せない。**`schedule_memo` は回次だけで引いているので、
  通常1回目とボーナス1回目を区別できない(既存の決めごと)。
  押せる回にだけ `rec-tap` を付け、ボーナスの行には付けない

## ダッシュボード

**顧客一覧タブの右**（`src/pages/Dashboard.jsx` / `api/dashboard.js`）。
「どの月が、どれだけ残っていて、誰に電話すればいいか」をここで見る。

### 数え方

- **期日が今日以前の回だけ**を数える。まだ期日の来ていない回は未回収ではない。
  支払日は人によって違うので、月の途中で分母が増える。それが正しい
- **100%回収できた月は出さない。**残っている月は、どれだけ古くても出し続ける
- **車を引き上げた方と、動作を試すための顧客は入れない。**
  引き上げた方に督促はしないし、試し打ちの金額を経営者に見せない
- 回収率は**回数(件)で数える。**「5/8 回収」= その月に期日が来た8回のうち8回中5回が入金済み。
  **一部入金は「回収」に数えない**（残りが1円でもあれば未回収）。
  未回収額のほうは残りだけを足すので、一部入金は反映される
- ボーナス回のある月は、その人が同じ月に2件出る。2回ぶんの入金が要るので正しい

### 行に出るもの

- 顧客名・料金（その回の予定額）。一部入金があれば「残り ◯円」を添える
- **後回し**＝まだ果たされていない入金約束（`promise.done = false`）。
  回次の入っている約束はその回の月へ、回次の無い約束は
  **その顧客のいちばん古い未回収の月**へ付ける（どの回か分からないため）。
  1件ならその中身、複数なら `1/2` のようにいちばん近いものと件数を出す
- **2つ以上の月に出ている顧客は赤背景**にして「◯か月 未回収」と出す。
  先月も今月も入っていない人が、いちばん先に電話する相手

行は名前順ではなく**金額の大きい順**。先に電話すべき相手が上に来る。

### 全期間をまとめた数字の帯は置かない（2026-08-07）

いちばん上に置いていた帯（回収率 `42% / 31-73回収`・未回収額・未回収の顧客・
その下の `2か月 10人` の内訳）は**丸ごと外した**。

見たいのは「**どの月が**どれだけ残っているか」で、それは月ごとの見出しに
`2026年6月分 25% 1/4回収 未回収 119,656円` として月ごとに出ている。
全期間を1つに丸めた数字は、そこから次に何をすればいいかが決まらない。

API も `合計`（全件・回収済み・率・未回収額・未回収人数・月数別）を**返さなくなった**。
どこからも読まないため。検算に要るときは `月` の各要素から数え直す
（検査の `未回収人数()` / `全体率()` がその例）。

### 約束切れ ─ まとめの1文と、行の印(2026-08-07 に作り替え)

**「この日に払う」と言った日を過ぎても入っていない**もの。
`promise.done = false` かつ `promised_on < 今日`。

**名前は並べない。**いちばん上には**件数のまとめを1文だけ**出す。

> 約束切れが 2026年6月分に 1件、2026年7月分に 2件、合計 3件 あります。

誰なのかは、下の月ごとの一覧で**その人の行に付く印**で分かる。

> 園田 将貴 ｜ 51,495円 ｜ `08/06 約束切れ`

名前を上にも並べると、下の一覧と**同じ人が二重に出て画面が伸びる**。
上は「どの月に何件あるか」だけを伝えて、下の一覧へ誘導する役に徹する。

**数えるのは行（顧客 × 月）。**画面で印の付く行の数とぴったり合う。
検査ではここを見ている（`合計 === 印の付く行の数`）。ずれたら数え方が壊れている。

- 同じ人でも、**未回収の月が2つあればその月ごとに1件ずつ**数える
  （どちらの月にも印が付くため）
- 逆に**未回収の月が1つなら、約束を何件足しても1件**。約束の行き先がその1行しかないため。
  その行の `後回し.件数` だけが増え、印は `08/06 約束切れ（2件）` になる

帯そのものを外したので（上記）、まとめの1文が**画面のいちばん上**に来る。

以前は名前を並べて「◯◯ さんが約束を破りました。」と出し、1人1行にまとめていたが、
下の一覧と重複するため取りやめた。

### 督促の連絡（`schedule.dunned_at` / `dunned_count` / `dunned_by`）

**「もう電話したか」を回ごとに控える。**

**顧客ごとに持たない。** 顧客に持つと、次の月になっても「督促済み」のままになり、
かけ忘れた人が分からなくなる。回が変われば、また「未督促」から始まる。

- 未入金タブで、名前の横の印そのものを押して控える
  （`POST /api/customer {種類:'督促', 回次, 回の種類}`）。
  **ボタンを増やさない。**電話を切った直後にその場で押せる場所に置く
- もう一度押すと回数が増える。督促済みの印を押すと取り消せる（`督促取消`）
- 未入金タブの見出しに「未督促 ◯名」を出す。かけ残しがひと目で分かる
- ダッシュボードでも、督促していない人に「未督促」の印を出す

### トラブルは外した（2026-08-07）

「携帯が繋がらない」「支払いに応じない」を `trouble` テーブルで持っていたが、
**メモと他の運用で足りる**という判断で外した。
既に作られたデータベースにテーブルが残っていても、どこからも読まない。

検査は `scratchpad/t-dash.js`（数字の検算）と `scratchpad/t-dashui.mjs`（画面）。

## デバッグ依頼

**設定タブの右**の「デバッグ依頼」タブ（`src/pages/Debug.jsx`）。
電話を受けている最中に画面のおかしさに気づいても、伝える先が無いと忘れてしまう。
その場で画面の写しを付けて出せるようにする。

- 依頼は **タイトル・本文・画像**。出したあと、**画像とメッセージで返信**できる
- 状態は **未対応 / 対応中 / 直した** の3つ。押すだけで変わる。
  一覧では「直した」を既定で隠す（隠した件数は出す）
- 依頼は**消せる**。記録(`event`)と違って追記のみにしていない。
  顧客の名前が写り込んだ画像を間違えて上げたとき、消せないと困るため。
  消すと返信と画像も一緒に消える（`ON DELETE CASCADE`）
- 台帳の数字とは関わりが無いので、**顧客や入金とは結び付けない**

### 画像をどこに置くか

**データベースの中(`debug_image.bytes`)に置く。**外の置き場は使わない。
置き場を増やすと設定と料金がもう1つ増え、動かなくなったときの原因が分かりにくい。

送る前に画面側(`src/shrink.js`)で小さくする。

- 原寸は**長辺1600px・JPEG品質0.85**。写した画面の文字はこれで読める
- 一覧に並べる**小さい版(長辺320px)**も一緒に作って `thumb` に入れる。
  一覧で原寸を何枚も読ませない
- 透けている部分は白で塗る。JPEGに透過は無く、塗らないと黒くなる

上限は**1枚およそ1MB・8枚まで・合計3.5MBまで**。
画面側とサーバー側の両方で止める。Vercel が1回の送信を 4.5MB までしか通さないため。

画像は `GET /api/debugimage?id=` で読む(`<img src>` から直に)。
**ログインしていない相手には返さない。**画面の写しには顧客の名前と金額が写る。
一度上げた画像は差し替わらないので `Cache-Control: private, max-age=31536000, immutable`。
共用の中継所には置かせないため `private`。

検査は `scratchpad/t-debug.mjs`。
