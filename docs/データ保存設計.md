# データ保存の設計

作成: 2026-07-27 / 状態: 承認待ち

いまの台帳は画面の中だけで動いており、**再読み込みするとすべて消える**。
実運用に向けて、記録をサーバーに保存する。方針は `引き継ぎ資料/docs/spec.md` の
データモデルに従い、順序も引き継ぎ資料の指示どおり
**契約 → 支払予定 → 入金 → 充当 → 事象 → 名寄せ辞書** で作る。

## どこに置くか

| | 選定 | 理由 |
|---|---|---|
| 置き場所 | Vercel + Neon(PostgreSQL) | 今の公開先がVercel。追加の管理先を増やさない |
| 通信 | 画面 → `/api/*` → データベース | 画面から直接データベースに触らせない |
| 認証 | いまの簡易ログインを流用し、後で担当者ごとの利用者に置き換える | 仕様どおり「ログインは後回しでよいが、記録の『誰が』欄は最初から持つ」 |

**バックアップはデータベース側の自動バックアップを使う。**
端末のブラウザには保存しない(端末を替えると消えるため、引き継ぎの目的に反する)。

## テーブル

金額はすべて**円の整数**(小数を使わない)。日付は日付型。

### 1. contract(契約)

| 列 | 型 | 備考 |
|---|---|---|
| id | serial | |
| name | text | 氏名 |
| kana | text | よみ。あいうえお順に使う |
| car | text | 車両 |
| tel / email | text | **連絡先。権限を分ける対象** |
| purchase_amount | int | 買取額 |
| fee_amount | int | 手数料 |
| total_amount | int | 支払総額。手数料 = 総額×25% を登録時に検算 |
| monthly_amount | int | 毎月額 |
| term_count | int | 回数。既定48 |
| pay_day | int | 支払日 1〜31。原則27、契約ごとの例外を認める |
| start_date | date | 支払開始日。原則、納車の翌月 |
| bonus_months | int[] | **ボーナス月。金額とは別の列**(文字列にしない) |
| bonus_each | int | ボーナス1回あたりの加算額 |
| bonus_remaining | int | ボーナス見込み残。入金があったときだけ減らす |
| balance_diff | int | 累計差額。マイナスが不足、プラスが前受 |
| diff_plan | enum | 未定 / 最終回 / 均等 / 別途請求 |
| status | enum | 通常 / 別あつかい(値は今後増やす。ADR-008) |
| delivered_on | date | 納車日 |
| memo | text | この方についてのメモ(書き直せる欄) |
| created_at / updated_at | timestamptz | |

### 2. schedule(支払予定)

契約登録時に回数ぶん自動生成する。**予定額は毎月額のみ。ボーナス加算を含めない(ADR-002)。**

`id, contract_id, no(回次), due_date, planned_amount, state`

### 3. payment(入金)

`id, contract_id, paid_on(受領日), deposited_on(預入日), amount, method(振込/現金/その他), receipt_no, recorded_by(記録者), source(手入力/全銀CSV), import_key, created_at`

- 現金は**受領日と預入日を別に持つ**(手元現金の照合のため)
- `import_key` は二重取込の検知に使う。全銀の照会番号は重複しうるため
  **日付+金額+振込依頼人名+連番**で作り、一意制約をかける

### 4. allocation(充当)

`id, payment_id, schedule_id, amount, kind`

kind は 元本 / 手数料 / 遅延損害金 / 値引 / 相殺 / 前受 / ボーナス。

**入金に予定IDを1本だけ持たせない(ADR-003)。** まとめ払いを1件の入金として受け、
複数の予定へ按分する。残高は Σ充当額 で出す。

**分割入金(1回ぶんを何度かに分けて払う)もこれで扱う。**
電話で「3日後に半分、5日後に残り」と言われるのが日常なので、
1回ぶんに複数の入金を充てられる必要がある。

- その回に入った額 = Σ(その回への充当のうち 元本・手数料)
- **満額に届くまで `schedule.state` は `一部入金`**。届いてはじめて `入金済み`
- **過不足はその回が終わったときだけ動かす。** 途中の不足は「この回の残り」として持つ
  (途中で不足を過不足に入れると、まだ払う約束がある分まで滞納に見えるため)
- 取消は残った充当から状態を決め直す(いつも `未入金` に戻すわけではない)

**毎月分とボーナスが1回の振込に混ざる場合も、これで扱う。** 実際によくある形で、
たとえば 108,755円 = 毎月分 78,755円 + ボーナス 30,000円。
**入金は通帳の1行と同じく1件**にし、充当を 元本・手数料(毎月分)＋ボーナス の3本に分ける。
2件に分けて記録しない(通帳と件数が合わなくなり、二重取込の判定も崩れるため)。

- 過不足は**毎月分だけ**で見る。ボーナス分は請求と関係しない
- ボーナス分は `contract.bonus_remaining` から引く
- 取消は両方それぞれ戻す(充当の kind ごとに合計して逆算する)

### 5. event(事象)— 追記のみ

`id, contract_id, no(回次), occurred_at, recorded_by, kind, text, memo`

kind は 請求 / 入金 / 遅れ / 未収 / 差額 / 約束 / 不履行 / 回収 / ボーナス / メモ / 取消。

**更新も削除もしない(ADR-005)。** 訂正は「取消」を足す。
データベース側でも更新・削除を禁止する(権限を絞る)。

### 6. payer_alias(名寄せ辞書)

`id, normalized_name(一意), contract_id, created_by, created_at`

一度人が紐付けたら永続化する。正規化は半角/全角カナの統一・法人格の除去・記号と空白の除去。
**同姓が実在する**(山田が2名、斎藤と齊藤がカナで同一)ため、
一致しないものは自動で決めず「本人を確かめる」に回す。

### 7. promise(約束)

`id, contract_id, heard_on, promised_on, amount, heard_by, memo, prev_due_date`

`prev_due_date` は**約束前の期日**。現在の画面は約束すると期日を更新する運用のため、
もとの期日をここと事象の両方に残し、滞納していた事実が消えないようにする。

**約束は1回ぶんに何件でも足せる**(分割のため)。上書きしない。
期日は**これから来る約束のうちいちばん早い日**にそろえる。
1件足すごとに期日が跳ね回らないようにするため。

## APIの形

Vercel の関数は1ファイル1エンドポイントなので、
種類をわけるのではなく **読む/書く/取り込む** の3本にまとめた。

| 用途 | |
|---|---|
| GET `/api/contracts` | 画面が使う一式(一覧・入金表・出来事・約束) |
| POST `/api/record` | 書き込み。`種類` で分ける(入金・ボーナス・約束・メモ・人メモ・よみ・取消) |
| ↑ `種類:'入金'` の `ボーナス分` | 1回の振込に毎月分とボーナスが混ざっているとき、そのうちのボーナス額 |
| ↑ `種類:'期日変更'` | 回ごとの期日を動かす(入金カレンダーから) |
| POST `/api/import` | 全銀CSVの取込(下記) |
| GET/POST `/api/opening` | 移行の3(開始時に何回目まで入金済みか) |
| GET/POST `/api/yomi` | よみ(カナ)をまとめて入れる |
| POST `/api/customer` | 新しいお客さん(手数料25%を検算、支払予定48回も作る) |
| POST `/api/setup` `/api/seed` | 移行の1〜2(テーブル作成・54件の投入) |

**書き込みはすべて記録者を伴う。** いまは簡易ログインの利用者名を入れ、
担当者ごとの利用者を作ったらそれに置き換える。

### `/api/import` の3つの呼び方

| 送るもの | すること |
|---|---|
| `{text}` | 読み取って照合するだけ。**まだ保存しない**。件数と明細を返す |
| `{text, 実行:true}` | お名前が決まった分だけ保存し、決まらなかった分を `残り` で返す |
| `{割当:{contract_id, iso, amount, payer, import_key}}` | 分からなかった1件を、人が選んだお客さんの入金にする |

ファイルの読み取り(Shift-JIS・和暦・半角カナ)も名寄せもサーバーで行う。
画面はファイルを文字に直して送るだけで、判定は持たない。

**二重取込を弾く鍵。** 全銀の照会番号は重複しうるので鍵に使えない。
`日付|金額|振込人名(正規化)|同一内の連番` を `payment.import_key` に入れ、
データベースの一意制約で弾く。同じファイルを二度読ませても増えず、
同じ日に同じ人から同じ額が2件あるときは2件とも入る。

**名寄せ。** まず `payer_alias`(前に人が紐付けた名前)、次に契約の「よみ」で当てる。
同姓が複数いるときは毎月額で絞り、それでも決まらなければ人に回す。
人が選んだ紐付けは `payer_alias` に覚えて、次回から自動で当たるようにする。

**よみは苗字だけでよい。** 銀行の振込依頼人名は「ｷﾑﾗ ﾕｳｽｹ」のように
下の名前まで入ることが多いので、ぴったり一致しなければ
**登録した読みで始まるか**で見る(長い読みを優先。2文字以上のみ)。
苗字だけの登録でもフルネームの振込に当たる。

ただし同姓が複数いると(実データでは田中3名・サイトウ2名・山田2名・松本2名)
金額でしか見分けられない。**下の名前まで入れれば**その迷いは消える。

## 移行(8月予定)

`引き継ぎ資料/docs/migration.md` の手順に従う。

1. 契約54件を投入。手数料 = 総額×25% を全件で検算
2. 各契約の支払予定を生成(ボーナス加算は含めない)
3. **開始時に一度だけ**、54件それぞれが何回目まで入金済みかを銀行明細で確認して入れる
4. 累計差額の初期値を入れる(既知:山本一馬さんの残金10,000)
5. 検算を通らなかったものだけを人に出す

移行前に決着が必要なもの: **B-1(ボーナス月3件)** と **B-2(2月シートの所在不明1件)**。

## 作る順序

1. ~~データベースを用意し、テーブルを作る~~ 済(`/api/setup`)
2. ~~読み取りAPIを作り、画面をサーバーのデータで描くよう差し替える~~ 済(`/api/contracts`)
3. ~~書き込みAPI(入金・約束・メモ)を差し替える~~ 済(`/api/record`)
4. ~~全銀CSV取込をサーバー側に移す(二重取込の判定はデータベースで行う)~~ 済(`/api/import`)
5. 移行データを投入 … 1・2は済(`/api/seed`)。3(開始時の入金実績)は
   銀行明細を見ながら人が入れる作業が残っている(`/api/opening`)

各段でいまの画面の動きを保ったまま差し替える。

5段すべて済み。新しいお客さんの追加も `/api/customer` で保存する
(支払予定48回・名寄せ辞書・記録まで作る)。
