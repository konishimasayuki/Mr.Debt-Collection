## 1. システム概要

### 1.1 何をするものか

自社割賦（車の自社ローン）の**入金管理台帳**です。

顧客ごとに「月々いくら × 何回」の支払予定を持ち、銀行から入ってきた入金を
どの回に充てるかを管理します。誰がいくら遅れているかを、電話を受けたその場で
出せるようにすることが目的です。

### 1.2 使う人

| 誰が | 何をするか |
|---|---|
| 電話を受ける担当者（新人・アルバイトを含む） | 入金の取り込み、入金約束の記録、顧客への応対 |
| 経営者 | 未収の総額と、遅れている人を見る |

**新人が電話を受けながら操作する**ことが前提です。画面の言葉づかい・確認の出し方は、
すべてこの前提で決めてあります。

### 1.3 やらないこと（スコープ外）

- 会計仕訳の作成、決算
- 債権回収の法的手続き
- 顧客本人が見る画面（社内専用）

## 6. データ設計

### 6.1 考え方

| 決めごと | 理由 |
|---|---|
| **金額はすべて円の整数** | 小数を使うと丸めでずれる |
| **期日は固定。約束では動かさない** | 「いつまでに払うと言ったか」と「いつが期日か」は別の話 |
| **記録（`event`）は追記のみ** | お金の跡を消させない。データベースのトリガで守っている |
| **充当は中間テーブルで持つ** | 1回の振り込みが複数の回にまたがるため |

詳しくは `docs/データ保存設計.md` を見てください。

### 6.2 テーブル一覧

**定義の正本は `api/_schema.js` です。**下は何のための表かの一覧です。

| テーブル | 何を持つか |
|---|---|
| `customer` | 顧客。契約の条件（月々の金額・回数・支払日・ボーナス払い）と連絡先 |
| `schedule` | 支払予定。1回ぶんが1行。`kind` で通常とボーナスを分ける |
| `payment` | 入金。銀行から取り込んだもの・手で入れたもの |
| `allocation` | 充当。どの入金を、どの回に、いくら充てたか |
| `promise` | 入金約束。「いつまでに払う」と言われた記録 |
| `schedule_memo` | 回ごとのメモ。電話で話したことをその回に残す |
| `company` | 債権譲渡会社・譲渡先 |
| `bank_account` | 銀行口座 |
| `bank_txn` | 銀行から取ってきた明細（取り込む前） |
| `payer_exclude` | 取り込まない振込人 |
| `payer_alias` | 振込人名と顧客の対応（名寄せ） |
| `event` | 記録。誰が・いつ・何をしたか。**追記のみ** |
| `debug_ticket` / `debug_message` / `debug_image` | デバッグ依頼 |

### 6.3 スキーマを変えるとき

**`api/_schema.js` に文を足します。**手でデータベースを触らないでください。

```js
// CREATE TABLE のほうにも足す（新しい環境用）
// そのうえで ALTER TABLE を足す（すでにある環境用）
`ALTER TABLE customer ADD COLUMN IF NOT EXISTS 列名 型`,
```

**鉄則：列を足す文は、その列を使う索引よりも必ず前に置いてください。**
順番を逆にすると、新しい環境でだけ失敗します。

#### 自己修復のしくみ

本番のデータベースには直接つなげません。そのため、
**「列が無い」「表が無い」で失敗したとき、`api/_db.js` が自分で `_schema.js` を流し直し、
もう一度やり直します。**つまずいた文は飛ばします。

注意点：

- **列も表も増えない変更（トリガの中身など）は、このきっかけが起きません。**
  過去に、トリガの変更が本番に届かず不具合になったことがあります
  （いまは「記録は追記のみです」で弾かれたときも流し直すようにしてあります）
- 流し終えたら手を空けます。二度目以降も効きます

### 6.4 接続の作法

`@neondatabase/serverless` の `neon(url)` は **`sql(text, params)` として呼びます。**

```js
const sql = db();
const rows = await sql('SELECT * FROM customer WHERE id=$1', [id]);
```

- **`sql.query()` はありません**
- **`BEGIN` / `COMMIT` の取引は使えません。**1つの問い合わせごとに別々に飛びます。
  途中で失敗すると、そこまでの書き込みは残ります。**書く順番で守ってください**
- 日時は `to_char(… AT TIME ZONE 'Asia/Tokyo', …)` で日本時間に直します。
  そのまま切ると、夜に書いたメモが前日の日付で出ます

### 6.5 速さの考え方

**問い合わせの「回数」ではなく「段数」を減らします。**
データベースは遠くにあり、1往復ごとに待ち時間がかかります。順に待つと足し算になります。

```js
const [顧客, 予定, 入金] = await Promise.all([ … ]);
```

互いに関係のない問い合わせは、必ず `Promise.all` で同時に投げてください。

- 全員が同じ利用者名とパスワードを使う**簡易認証**です
- クッキーにセッションの合鍵を入れます（8時間）
- 合鍵は `SESSION_SECRET` と利用者名・パスワードから作ります。
  **パスワードを変えれば、古いクッキーは自動で使えなくなります**
- 記録者はすべて「管理者」で入ります。**担当者ごとの利用者は未実装です**（「15. 引き継ぎ事項」）

### 7.4 定期実行

| 何を | いつ | 守り |
|---|---|---|
| 銀行から入金明細を取ってくる | 毎日 22:00 UTC（日本時間 7:00） | `CRON_SECRET` |

**`CRON_SECRET` を決めていない環境では動きません。**誰でも叩けてしまうためです。

**定期実行からできるのは取得だけです。**口座も入金も変えられません。
取ってきた明細は `bank_txn` に置くだけで、台帳への取り込みは人が確認して行います。

## 8. 業務ルール

**ここが、この台帳でいちばん壊しやすいところです。**
直す前に、必ず該当する検査を読んでください。

### 8.1 充当（どの入金を、どの回に充てるか）

- **古い回から順に埋めます。**「1回目は未入金なのに3回目は入金済み」を作りません
- 詰める順は**記録した順（id 順）**です
- 状態は 未入金 / 一部入金 / 入金済み の3つ
- **ボーナスの回に入れてよいのは、人がボーナスと決めた入金だけです。**
  同じ日に月額とボーナスが並ぶと、金額の大きいボーナスが先に埋まってしまうためです
- 入金種類は 月額（`通常`）/ ボーナス / 月額＋ボーナス（`両方`）。
  指定が無ければ月額として扱います

書き込みのあとは、必ず `詰め直す(sql, customerId)` を呼んでください。
呼び忘れると並びが崩れます。

### 8.2 期日

- **期日は固定です。**入金約束では動きません
- 動かせるのは3つだけです
  - 顧客編集の**支払い開始月・毎月の支払日** … 全部の回
  - 顧客編集の**入金月の変更** … 未払いの回から先だけ（理由の記入が必須）
  - 支払いの記録の**賞与の移動** … その1回だけ
- その月に無い日（31日など）は**末日**にします

### 8.3 ボーナス払い

- 月は複数選べます（例：7月と12月）。日と金額は共通です
- **回数を決めたときは、契約の最終回より後になっても作ります。**
  賞与は払う約束をしたお金です。入る月が足りないからと落とすと、台帳から債権が消えます
- 回数を決めていなければ、契約の期間に入るぶんだけ作ります
- **入金が充てられているボーナスの回は消しません。**入金の行き先が消えるためです
- 移したあと、賞与の番号は期日の古い順に振り直します。
  **回のメモも一緒に付け替えます。**片方だけ直すとメモが別の回に付きます

### 8.4 金額

- **顧客情報の編集では、月々の金額と支払回数を変えられません。**
  変えると支払予定をまるごと作り直すことになり、すでに充てた入金の行き先が消えます
- これからの金額は、**支払いの記録の未払いの回から**変えます。
  押した回から先の、入金の無い回だけを書き換えます（理由の記入が必須）
- 支払総額は、支払予定を足し直して出します。手で計算するとずれます

### 8.5 顧客の削除

- **入金が1件でもあれば消せません。**1円でも受け取っていれば、守るべきお金の跡があります
- 消せるのは入金が0件の顧客だけです（登録し間違えたとき）
- 消したことは、顧客に結び付かない記録として残します

### 8.6 記録（`event`）

**追記のみです。**更新も削除もできません。データベースのトリガで守っています。
例外は「入金が1件も無い顧客の記録」だけです（顧客ごと消すため）。

## 13. セキュリティ

### 13.1 決めごと

- **鍵はリポジトリにもデータベースにも置きません。**環境変数から読みます
- **定期実行は合言葉を決めていない環境では動きません**
- **定期実行からできるのは取得だけです。**口座も入金も変えられません
- 検索避け（`X-Robots-Tag: noindex, nofollow`）を全ページに付けています
- 社内専用です。顧客本人に見せる画面はありません

### 13.2 扱っている個人情報

| 何を | どこに |
|---|---|
| 氏名・よみ・性別・生年月日・住所・電話番号 | `customer` |
| 連帯保証人・緊急連絡先（氏名・住所・電話番号・間柄） | `customer` |
| 入金の記録（金額・日付・振込人名） | `payment` / `bank_txn` |
| 電話で話した内容のメモ | `schedule_memo` / `customer.memo` |

**個人情報を外部へ出す機能はありません。**デバッグ依頼の転送だけが外に出ますが、
本文のテキストのみで、画像は送りません。

### 13.3 してはいけないこと

- 本番のデータベースを手で直す（`_schema.js` を通してください）
- `event` テーブルを直接消す
- 鍵の値を文書・チャット・コミットに書く
- 入金のある顧客を消そうとする

## 14. 用語集

| 言葉 | 意味 |
|---|---|
| 自社割賦 | 車の販売店が、自社で分割払いを組む仕組み |
| 支払予定（`schedule`） | 「何回目・いつ・いくら」の1行 |
| 充当（`allocation`） | どの入金を、どの回に、いくら充てたか |
| 詰め直す | 充当を、古い回から順に組み直すこと |
| 回（かい） | 支払いの1回ぶん。通常の回とボーナスの回がある |
| 賞与 / ボーナスの回 | 賞与月にまとめて払う回 |
| 名寄せ | 銀行の振込人名から、どの顧客かを当てること |
| よみ | カナの氏名。銀行の明細がカナで来るため、名寄せに使う |
| 引き上げ | 車を引き上げて取引を終わりにすること（督促も請求もしない） |
| 除外リスト | 取り込まない振込人（社内の振替など） |

### 15.2 気をつけるところ

| どこ | 何に気をつけるか |
|---|---|
| 充当の処理（`api/_lib.js` の `詰め直す` / `充てる順`） | ここを直すとお金の並びが変わります。検査を必ず読んでください |
| `api/_schema.js` | 列を足す文は、その列を使う索引より前に置いてください |
| `api/_db.js` の自己修復 | 列も表も増えない変更は、きっかけが起きません |
| 取引が使えないこと | `BEGIN` / `COMMIT` がありません。途中で失敗すると、そこまでの書き込みが残ります |

### 15.3 過去の判断と、その理由

| 決めたこと | なぜ |
|---|---|
| フレームワークを入れない | 人手が少なく、版上げに追われたくない。素の React で足りている |
| 変数名も日本語 | 業務の言葉とコードの言葉を一致させ、業務に詳しい人が読めるようにする |
| 記録を追記のみにする | お金の跡を消させない |
| 期日を固定にする | 「いつまでに払うと言ったか」と「いつが期日か」を混ぜない |
| 賞与を契約の外にも作る | 落とすと、払う約束をしたお金が台帳から消える |
