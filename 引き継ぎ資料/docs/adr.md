## ADR-001: 契約を1件1行で持ち、支払予定を別テーブルに生成する

日付: 2026-07-23 / 状態: 採用

### 文脈

既存のスプレッドシートは月ごとにシートを分けており、各シートは「その月に納車した契約の一覧」だった。
入金状況はチェックボックス1つしかなく、**2回目から48回目までの入金を記録する場所がどこにもない**。
3月に納車した7名が現在何回目まで払ったのかを、この資料から復元できない。

### 決定

契約は1件1行。契約登録時に48回分の支払予定を自動生成し、消し込みは「予定 対 実績」の照合とする。
予定日を過ぎて未消込のレコードを抽出すれば、それがそのまま督促リストになる。

### 検討した代替案

- 月シートを維持して行を増やす — 同じ契約が複数シートに散り、滞納の連続性が見えない
- 入金明細を起点に消し込む — 現金手渡しが銀行明細に現れないため、起点にできない

### 帰結

毎朝の目視がクエリ1本になる。督促漏れの検知が自動化される。
コストとして、契約登録時の入力項目が増える(ボーナスの月と金額を分けるなど)。

## ADR-002: ボーナス加算を支払予定に含めない

日付: 2026-07-24 / 状態: 採用

### 文脈

支払総額と「毎月額×48」の差が全社で 7,368,006円 ある。これは契約書上の確定事項ではなく、
スプレッドシートのメモにすぎない。実際に払われるかどうかは不確実。
予定に入れると、払わない契約が毎月「不足」と判定され、赤が常態化して本当の滞納が埋もれる。

### 決定

月々の請求は毎月額のみ。差分は契約に「ボーナス見込み」として1つ持ち、督促の対象にしない。
入金があれば見込みから減らす。減らないまま回次が進むと回収見込みが悪化するため、
**毎月額の10回分を超えた契約を「ボーナス依存が重い」として別に出す**。

### 検討した代替案

- 予定に含める — 上記の理由で却下
- 何も持たない — 48回払い終えても総額に届かない事実が見えなくなる

### 帰結

督促の精度が上がる。一方で、宇佐美さん(毎月額の35.6回分)のように
**48回では到底回収できない契約が可視化される**。これは設計の副産物だが、経営判断の材料になる。

## ADR-003: 差額は回ごとではなく契約単位の累計残高で持つ

日付: 2026-07-23 / 状態: 採用

### 文脈

顧客が請求と違う金額を振り込むことが多い。端数を切る、振込手数料を引かれる、多めに払うなど。
既存データにも「残金10,000」というメモがあり、これは部分入金の残額だった。

### 決定

契約に累計差額(預り残高)を1つ持ち、入金額と請求額の差を積む。マイナスが不足、プラスが前受。
充当は中間テーブル `充当(入金ID, 予定ID, 充当額, 区分)` で表現し、区分に
元本・手数料・遅延損害金・値引・相殺を持つ。残高は Σ充当額 で算出する。

差額が出たときの処理は担当者が選ぶ。次へ繰り越す / 精算して0にする / ボーナス分に充てる。
どれを選んだかを記録に残す。

### 検討した代替案

- 回ごとに「一部入金」状態を持つ — 端数が延々と残り、どの回に紐づくかで運用が混乱する
- 入金レコードに請求IDを1本だけ持つ — まとめ払いで即座に破綻する

### 帰結

多く払われても少なく払われても同じ仕組みで扱える。
コストとして、残高の初期値を移行時に入れる必要がある。

## ADR-004: 信用スコアを保存せず、事象を保存する

日付: 2026-07-24 / 状態: 採用

### 文脈

支払いの滞りを数えて信用スコアの土台にしたい、という要望があった。

### 決定

保存するのは事象(いつ・誰が・何が起きたか)だけ。スコアは都度計算する。
記録する事象は、請求・入金・遅れ・未収・部分入金・約束・約束の不履行・回収・ボーナス入金・メモ。

集計は生の回数だけでなく **最長の連続滞納** と **約束を破った回数** を分けて数える。
1回ずつ5回遅れた人と、5ヶ月連続で止まっている人は別物であるため。
加点(ボーナス入金、無遅延)も持つ。減点だけだと、事象ゼロの41件が全員同じに見える。

### 検討した代替案

- スコアを都度保存する — 後から「直近1年を重く見たい」となったとき遡って計算し直せない

### 帰結

スコアの式をいつでも変えられる。実績が半年溜まってから、実際に焦げ付いた契約の
特徴を見て式を決める方が精度が出る。**今は式を決めないこと自体が決定である**。

## ADR-005: 記録は追記のみとし、書き換えを許さない

日付: 2026-07-23 / 状態: 採用

### 文脈

督促の履歴を、担当者以外にも説明できる形で残したいという要望があった。

### 決定

事象テーブルは追記のみ。訂正は「取り消した」という事象を足す。回次ごとにまとめた時系列で表示する。
割賦は回次が業務の単位なので、単純な時系列よりも回次でグループ化した方が読みやすい。

### 検討した代替案

- 編集可能なメモ欄 — 既存スプレッドシートのメモ欄と同じ構造になり、
  「言った言わない」を防げない

### 帰結

督促の経緯を初めての人が読める。割賦販売法上の催告の証拠にもなり得る(要弁護士確認)。
コストとして、誤記録が残る。ただし訂正の事実が見えることの方が価値が高い。

## ADR-006: 通帳との照合は、システムの計算額を伏せてから入力させる

日付: 2026-07-23 / 状態: 採用

### 文脈

明細の一括取り込みは便利だが、確認せずに確定できてしまう点が危険という指摘があった。
一方、成功分を1件ずつ確認させると流し読みになり、形だけの確認が残る。

### 決定

人が確認するのは2つだけ。**通帳の合計が合っているか**と**落ちた人の名前**。
通帳の金額を入力してもらい、**入力後に**システムの計算額を開いて突き合わせる。
一致しなければ確定させない。ファイル自体の検算と二重取込の検知は自動で行い、画面に出さない。

### 検討した代替案

- 計算額を先に表示して「合っている/合っていない」を押させる — 人は表示された数字を写すだけになり、
  確認が形骸化する。統制として一段落ちる
- 1件ずつ確認 — 正しさを増やさず手間だけ増える

### 帰結

入力は数字1つで済み、かつ本物の検証になる。
銀行APIを接続した時点で、この確認は機械が行い人の作業から消える。**現状は暫定である**。

## ADR-007: 差額のしきい値を督促にだけ適用し、完済前には適用しない

日付: 2026-07-23 / 状態: 採用

### 文脈

振込手数料ぶんの数百円が大量に発生する。すべてを督促対象にすると赤が増えすぎて、
本当にまずい契約が埋もれる。一方、完済時に1円でも合わないと完済処理ができない。

### 決定

日常の督促は 1,000円以上のみ対象。完済前の精算は金額に関係なく全件、残り12回から案内する。
**同じ差額を、平時は無視して完済前は無視しない。** 一本のルールにすると必ずどちらかが壊れる。

しきい値未満の差額も画面には表示する(灰色)。見えるが騒がない状態にする。

### 検討した代替案

- 一律のしきい値 — 完済時に端数が残り、帳尻が合わない
- しきい値なし — 数百円の行が並び、10,000円の不足が埋もれる

### 帰結

しきい値1,000円は暫定。実際の振込手数料の実績を見て調整する前提。

## ADR-008: 日々の消し込みから外れた契約は「状態」で管理する

日付: 2026-07-24 / 状態: 採用(実装は未着手)

### 文脈

車両を回収した契約が「遅れ」に混ざっていた。引き揚げ済みの契約に督促電話はかけない。
やることは残債の処理であり、日々の消し込みとは別の仕事。
また未収の合計に回収済みを混ぜると、督促で取り返せる金額が実態より大きく見える。

### 決定

契約に「状態」欄を持たせ、日々の消し込みから外れたものを別扱いにする。
値は今後増える(回収・契約解除・支払い猶予・相続手続中・弁護士介入など)。

**タブ名を「回収」にしない。** 回収は取り立てを進める状態、弁護士介入は取り立てを止める状態で、
扱いが正反対のものが同じ枠に並ぶと、督促してはいけない相手に連絡する事故が起きる。

**状態ごとに請求の扱いを固定し、担当者が自由に選べるようにはしない。** 状態が決まれば
請求を止めるかどうかは自動的に決まる。手で選べるようにすると、状態と請求が食い違った
契約が生まれ、半年後に誰も説明できなくなる。既存スプレッドシートのメモ欄と同じ構造である。

状態を変えるときに、その状態で許される選択肢の中から今後の請求の扱いを選ばせ、理由をメモに残す。

### 検討した代替案

- 請求リストから外す/外さないのトグル — 上記の理由で却下
- 契約を削除する — 残債が消える。回収3件で 5,712,145円 が残っている

### 帰結

状態の一覧と、それぞれの請求の扱いを決めるまで実装できない(open-questions B-7, B-8)。
欄だけは先に作ってよい。値を増やすのは安いが、欄を後から足すのは全件の見直しになる。

## ADR-009: 画面と仕組みを5つのタブに作り替える

日付: 2026-07-31 / 状態: 採用

### 文脈

台帳は1枚のHTMLモックから育ってきたため、画面の骨格が「ダッシュボード + 契約カード」に
なっていた。担当者の実際の仕事は、電話を受けて約束を足すことと、銀行のCSVを取り込むことと、
遅れている人を数えることの3つで、そのどれもがダッシュボードの奥にあった。

利用者は入りたての担当者(場合により短時間勤務)である。**どこを押せば何ができるかが
ヘッダーで完結している必要がある。**

### 決定

画面を **顧客一覧 / 入金登録 / 入金履歴 / 未入金 / 設定** の5タブに作り替える。
スタックは **React + Vite**。ルーターも状態管理ライブラリも入れない
(タブの切替とモーダルだけで、URLを共有する用途がない)。

テーブルとAPIも作り替える。旧版の `contract / record / opening / yomi / gate` は
捨て、`customer / customers / payments / import / companies / setup / session` に置く。
既存の54件は `POST /api/setup {載せ替え:true}` で新しい形へ入れる。

**「入金登録」と「入金履歴」を別のタブにする。** 同じ画面に混ぜると、
取り込みの確認中に履歴を触ってしまう。入れる仕事と直す仕事は手が違う。

**未入金タブの行を押したら、入金履歴タブへ移り、その顧客名で検索した状態にする。**
遅れている人を見つけた次の動作は必ず「この人、いつ最後に入れた?」なので、
そこまでを1押しにする。

### 捨てた案と理由

- **ダッシュボードを残して5タブを足す** — 入口が2つになる。
  入りたての担当者に「まずダッシュボード、ただし取り込みはタブから」と教えることになる
- **Next.js** — サーバー側で描く必要がない。ログイン後は全画面が要ログインで、
  検索エンジンにも載せない。ビルドと運用の重さに見合わない
- **1枚のHTMLのまま直す** — 1文字直すのに置換スクリプトが要る状態だった(HANDOFF「罠」)
- **旧テーブルを残したまま新画面を載せる** — `contract.bonus_months` のように
  新画面で一度も読まない列が残り、次の担当者が「これは使われているのか」で止まる

### 帰結

**ボーナス加算・督促とめ・契約の状態・累計差額・現金の預入日・充当の kind・
オープニング(開始時の入金実績)を、いまは持っていない。**
一覧は `docs/データ保存設計.md`「今回落としたもの」にある。戻すときは git の履歴から取る。

このうち**オープニングの欠落が最も重かった**。載せ替えただけでは全員が1回目から
未入金に見えるため、2026-07-31 に `/api/opening` を作り直して戻した(B-20)。
旧実装は `schedule.state` を書き換えるだけで入金レコードを作っておらず、
入金済みなのに金額が0円のままだったので、今度は入金と充当まで作っている。
ADR-002(ボーナスを支払予定に含めない)は結論としては生きているが、
ボーナス見込みを持つ列そのものが無くなったため、載せ替え時に顧客のメモへ文章で残している。
